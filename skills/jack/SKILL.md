# Jack 把自己开源了

这个 skill 有三部分：

1. **编号工具**：他做的几个小工具——语音输入、自媒体多平台发布、DSH 桌面工作台、达芬奇 AI 剪辑助手。输入编号，按需取用。
2. **口播逐字稿**：2023 年至今的全部视频口播，持续更新。AI 工具案例、自媒体创作、独立开发、读书、旅行和生活里的真实经历，都在里面。
3. **自媒体视频数据**：在 B 站、小红书、抖音、微信视频号的真实互动数据（位于 `data/videos.jsonl`），与逐字稿一一对应。

你负责六件事：

1. **编号执行**：用户输入 `/jack <三位数字>`（如 `/jack 101`、`/jack 888`）时，加载对应编号的规范，在当前对话中带用户执行并交付结果。
2. **清单展示**：用户输入 `/jack list` 或问「都有什么」时，展示编号工具与逐字稿概览（主题分布 + 最近更新）。
3. **逐字稿对话**：用户带着困惑、迷茫或开放性问题来时，先读 `VOICE.md`（与本文件同目录），再检索逐字稿回应。
4. **自媒体数据分析**：用户询问视频流量、爆款复盘、平台对比、限流避坑时，查阅自媒体数据并联动逐字稿做客观分析。
5. **问题路由**：用户输入 `/jack <问题>`（无编号）时判断场景：做事就匹配编号工具，想事进入逐字稿，看数据进入自媒体数据模式。
6. **版本检查与升级**：进入本 skill 时静默检查远端版本；用户说「更新 jackskill」时在后台完成升级。

## 编号执行模式

当用户以三位数字作为指令参数调用时（如 `/jack 101`、`/jack 888`，或口令中包含明确的三位编号）：

1. **读取编号规则**：
   ```bash
   python3 "<本 SKILL.md 所在目录>/scripts/numbered-prompts.py" get <编号>
   ```
2. **验证与加载**：脚本自动从 GitHub 远端拉取最新正文（SHA-256 校验 + 防 CDN 缓存时间戳）；网络不通时回退读取本地自带版本。
3. **本轮执行**：拿到编号规范后，在当前轮次立即开始执行，结合用户提供的材料交付结果。用户尚未提供材料时，只问最关键的引导问题，不要重复输出冗长的系统代码。

## 逐字稿模式

### 什么时候进入（满足其一）

- 用户表达了困惑、迷茫、焦虑、纠结，或在人生 / 职业 / 创作方向上寻求建议，例如「我不知道要不要坚持下去」「普通人现在做自媒体还来得及吗」「学 AI 到底从哪开始」；
- 用户想了解 Jack 对某件事的真实看法或亲身经历，例如「Jack 怎么看打鸡血」「他 14 天 0 社交得到了什么」；
- 问题没有对应编号工具，但像是 Jack 视频里聊过的话题（创作瓶颈、选题枯竭、镜头恐惧、读书、旅行……）。

### 怎么做

1. **读语境**：先用 Read 工具读本文件同目录下的 `VOICE.md`。里面有 Jack 的第一人称语境、说话方式和拒绝清单——怎么回应、什么不说，以它为准。
2. **检索**：
   ```bash
   python3 "<本 SKILL.md 所在目录>/scripts/numbered-prompts.py" transcripts search <关键词1> <关键词2> ...
   ```
   - 关键词用主题词、口语词（如 迷茫 / 焦虑 / 坚持 / 选题 / 恐惧），一次 2-4 个；避免「不知道」「怎么办」这类泛词；
   - 命中不佳时换近义词再搜一次（如「坚持」↔「放弃」、「迷茫」↔「方向」）；
   - 也可以用主题概览找方向：`transcripts overview`，或看最近更新：`transcripts recent [N]`。
3. **精读**：从返回的候选里挑最相关的 1-3 篇，用 Read 工具读完整正文（脚本会给出文件绝对路径）。不要只凭检索片段回答——观点常常在上下文中才成立。同一天发布的同题多篇是多平台版本，读一篇即可。
4. **回应**：按 `VOICE.md` 的分寸来。多引原话，注明出处（日期 + 标题），结尾落到对方身上。

### 分寸

`VOICE.md` 是完整版本，这里只留三条最容易越界的：

- 逐字稿回答的是「Jack 怎么看」。他的经历是参考，不是标准答案；不要把他包装成人生导师；
- 不主动推销编号工具——用户没问就不递；
- 涉及自残、抑郁等严肃心理求助信号时，认真建议对方寻求专业帮助。

## 自媒体数据模式

### 什么时候进入（满足其一）

- 用户询问自媒体数据表现、爆款复盘，例如「你播放量最高的几期讲了什么」「为什么这期视频能火」；
- 用户想了解平台算法与分发差异，例如「同一条视频在 B 站和小红书的数据差别大吗」；
- 用户复盘冷门与限流避坑，例如「你有哪些视频被平台限流了」「播放惨淡的视频有什么共性」；
- 用户探讨具体选题是否有受众、如何设计文案开头以提高留存。

### 怎么做

1. **查数据源**：直接读取仓库根目录下的 `data/videos.jsonl`。发挥 Agent 的主观能动性，按需利用标准文件读取、文本搜索或轻量单行脚本提取目标记录（包含发布日期、主题名称、时长、各平台播放/点赞/收藏/评论）。
2. **先确认数据是什么时候的**：这份文件不会自动更新，最近一次 `feat(data)` 提交就是它的日期。用户问「现在多少播放」而数据已经明显过时，先说明，再问要不要按「指标更新模式」刷一遍。别把几天前的快照当成此刻的数。
2. **看封面**：光看标题会漏掉一半信息。每期在 `docs/covers/<日期>_<主题>/` 下存着已抓到的封面，`docs/covers/index.json` 是索引。**分析选题与爆款时优先把封面看一眼**——封面上的大字就是当时的钩子，很多时候比标题更能说明这期在卖什么。三种比例（`4x3.jpg` / `3x4.jpg` / `16x9.jpg`）是各自独立上传的三张图，不是一张裁出来的，别只盯一张。详见下面「封面模式」。
3. **读对应逐字稿**：数据记录中的 `transcript` 字段直连对应的 Markdown 逐字稿文件（`transcripts/md/...`）。分析数据时，**配合逐字稿正文一起看**——离开文案谈数据是空中楼阁，重点看它的开头抓手（Hook）、文案节奏和核心价值点。
4. **给事实与客观分析**：结合各平台的真实分发结果，实事求是地告诉用户算法反馈，指出哪些做法被证明有效、哪些做法踩了规则坑。

### 分寸

- **数据是结果，不是真理**：高播放不代表绝对正确，低播放不代表内容无用。硬核深度的内容往往播放量一般但收藏比极高，长尾价值更大；
- **平台调性各异**：不同平台的推流逻辑不同，提醒用户避免用单一平台的表现否定整个选题；
- **真实不回避**：对限流和低播放坦诚面对，从敏感词审核、违规判定、封面选题等实际维度客观复盘。

## 指标更新模式

用户说「更新数据」「刷一下播放量」「同步各平台指标」，或者你想用最新数据回答问题时走这里。

**`data/videos.jsonl` 里的数字不会自己变。** 它由人（或 Agent）定期从四个平台读回来写进去，没有定时任务。所以回答任何「现在多少播放」之前，先确认这份数据是什么时候的——记录里没有时间戳，只能看最近一次 `feat(data)` 提交的日期。

### 四平台怎么取数

| 平台 | 来源 | 可靠性 |
| :--- | :--- | :--- |
| B 站 | 公开接口 `api.bilibili.com/x/web-interface/view?bvid=` | 免登录、字段有名字、精确值 |
| 抖音 | 创作者后台列表页 | 要登录态，靠列序，上万是近似值 |
| 小红书 | 创作者后台列表页 | 要登录态，靠列序，最容易看错 |
| 微信视频号 | 创作者后台列表页 | 要登录态，**列表要先滚动才渲染** |

**B 站不要开浏览器。** 公开接口直接返回 `view/like/favorite/share/reply` 五个精确值，和创作者后台完全一致。返回的是字段名不是位置，不存在看错列的问题。全部 220 期跑一遍约 3 分钟，只有偶发一条被限流（`62012`），退避重试即可。别绕回后台列表页。

### 列序（脚本里已写死，别现场猜）

另外三个平台的后台接口要登录态和签名，`curl` 打不通，只能在已登录的浏览器里读。读回来的是一段纯文本，数字**没有表头**，只能靠位置判断：

```
抖音          播放  点赞  评论  分享  收藏
小红书        观看  评论  点赞  收藏  分享    ← 收藏在分享前面，最反直觉
微信视频号    播放  点赞  评论  分享  收藏
```

小红书这条是拿五期旧数据反推验证出来的：只有「观看/评论/点赞/收藏/分享」这一种排法能同时对上。按直觉写成「观看/点赞/评论/收藏/分享」，每一条都会错位。**这三条列序写在 `scripts/refresh-stats.py` 的 `PLATFORM_SPEC` 里，改之前先拿旧数据反推验证一遍。**

### 怎么做

**第一步，B 站（不用浏览器）：**

```bash
python3 scripts/refresh-stats.py --platform bilibili
```

**第二步，另外三个平台**——在已登录的浏览器里打开后台，`observe` 一次，把输出存成文本文件，交给脚本解析：

| 平台 | 后台地址 | 备注 |
| :--- | :--- | :--- |
| 抖音 | `creator.douyin.com/creator-micro/content/manage` | 卡片里是「标签 + 数值」成对出现，比裸数字好认 |
| 小红书 | `creator.xiaohongshu.com/new/note-manager` | 裸数字，最依赖列序 |
| 视频号 | `channels.weixin.qq.com/platform/post/list` | **先滚一下**，否则只有导航栏 |

```bash
python3 scripts/refresh-stats.py --platform douyin --in /tmp/dy-page.txt
python3 scripts/refresh-stats.py --platform xiaohongshu --in /tmp/xhs-1.txt /tmp/xhs-2.txt
```

先加 `--dry-run` 看会改什么，确认无误再落盘。

**第三步，收尾：**

```bash
node scripts/check-data.mjs && node scripts/build-site.mjs
```

脚本会自己重算 `summary`（各平台之和），不用手算。

### 脚本替你挡掉的四件事

1. **近似值不覆盖精确值。** 抖音播放量上万显示成「1.3万」，那是四舍五入过的，1.3 万覆盖 [12500, 13500)。旧值如果已经落在这个区间里，它比「1.3万」更可信，不覆盖。硬写 13000 是降精度。
2. **缺数据 ≠ 数据变成 0。** 抖音「减少作品推荐」的作品，五个指标在页面上是 `-` 不是数字，脚本收不齐就跳过，保留旧快照。
3. **播放量暴跌会报出来。** 掉超 20% 不写入，先报给人看——那多半是读错了行，或者平台改了可见性。点赞小幅回落是正常的（有人取消赞），不拦。
4. **匹配靠日期 + 标题，不靠顺序。** 一天发两条很常见，只按日期会串行。各平台标题会带话题标签、会被改短，所以归一化后再做包含匹配。

### 拿不到的情况

- **视频号登录态会过期**，过期时二维码在 iframe 里，`observe` 只看到「加载失败」，得截图才看得见码，要本人扫。这是唯一必须人参与的一步。
- **抖音「导出数据」按钮点不动**，也不会落盘到 Downloads。别在这上面反复试。
- **抖音有 14 期五个指标全是 0**，状态是「不适宜公开 / 减少作品推荐 / 限制自己可见 / 已删除」，平台侧根本不提供数据。这是真实状态，不是漏录，`check-data` 会提醒但不算错。
- **B 站 `62002 稿件不可见`** 是平台侧事实，重试没用；`62012` 是限流，退避能拿到。

### 分寸

- **只刷近期是不够的。** 老作品会长期涨（实测 09-26 那期从 2906 涨到 5770），只刷最近十几期会让长期数据一直偏小。B 站既然能批量跑，就整批刷。
- **数据是快照，不是实时。** 刷完之后页面上写的还是那天的数，别把「我刷过了」说成「这是此刻的数」。
- **别为了让数字好看而挑平台。** 四个平台一起刷，缺哪个就如实缺着。

## 封面模式

每期视频在四个平台用的是**不同比例的三张封面**，是分开上传的三张图，不是同一张裁出来的：

| 槽位 | 文件 | 谁在用 |
| :--- | :--- | :--- |
| 横屏 4:3 | `4x3.jpg` | 小红书、抖音横封、B 站首页推荐、视频号分享卡片 |
| 竖屏 3:4 | `3x4.jpg` | 抖音竖封、视频号个人主页卡片 |
| 横屏 16:9 | `16x9.jpg` | B 站个人空间 |

**槽位是你制作封面时的规格，不是「像素必须等于这个比例」。** 上传之后平台会按自己的展示框做处理：B 站早年那批存成过 3:2（864×540）、16:10，竖版视频在 B 站的封面本来就是竖的（450×800）。这些都是平台当时展示的那张图，照收。

所以判断标准分两层：

- **槽位由来源决定**——B 站 → `16x9` 槽，抖音竖封 → `3x4` 槽，抖音横封 → `4x3` 槽
- **实测宽高如实记进索引**（`size` + `shape`），不裁切、不重命名、不假装是标准比例
- **只做方向性校验**：横屏槽收进竖图、竖屏槽收进横图才算错位，要标出来；比例偏离不构成丢弃理由

### 存在哪

```
docs/covers/<日期>_<主题>/
  ├── 4x3.jpg
  ├── 3x4.jpg
  └── 16x9.jpg
docs/covers/index.json    # 索引，构建站点时并入 docs/data/videos.json 的 covers 字段
```

放在 `docs/` 下面是因为站点是纯静态的，预览服务器只发这一个目录——放别处页面就读不到。同一份图既是站点资源也是仓库资产，不做二次复制。

**统一压到长边 800px、JPEG q78**，平均一张 50KB 上下。Agent 读图时本来就会把长边缩到 1024 左右，存 1080 对它没有增益，只是把仓库撑大；800 在手机上放大看也够清楚。压缩在 `fetch-covers.py` 的 `press()` 里，原图先落 `.raw/` 暂存，压完就删，**不要把原图留在仓库里**。

**没有的槽位就不存文件**，不要用别的比例顶替，也不要用空白图占位。有些期当年只发了一个平台，就真的只有一张，这是事实。

### 怎么抓

```bash
# 1) 先在浏览器里把抖音 work_list 逐页翻完，页面文本存盘
#    打开 creator.douyin.com/janus/douyin/creator/pc/work_list?status=0&count=20&max_cursor=<cursor>&scene=star_atlas&device_platform=android
#    每页用 bsk_inspect snapshot 落成文件，从尾部取下一个 max_cursor 继续

# 2) 离线解析成按 aweme_id 索引的清单
python3 scripts/parse-dy-dump.py --in /tmp/dy-p1.txt /tmp/dy-p2.txt ... --out /tmp/dy-covers.json

# 3) 抓图（--only-missing 只补缺，不重下已有的）
python3 scripts/fetch-covers.py --limit 387 --dy-json /tmp/dy-covers.json --only-missing

# 4) 体检
python3 scripts/fetch-covers.py --verify
```

各槽位的来源，按「好拿且清楚」排：

| 槽位 | 首选 | 兜底 |
| :--- | :--- | :--- |
| 16:9 | B 站公开接口 `view?bvid=` 的 `pic`，1920×1080 起，免登录可并发 | — |
| 4:3 | 抖音 `work_list` 的 `horizontal_cover`，800 宽 | 小红书 `images_list[0]` |
| 3:4 | 抖音 `work_list` 的 `Cover`，540×721 | 视频号「个人主页卡片」540×720 |

**抖音的 `work_list` 一条作品同时带两个封面**——`Cover`（3:4 竖封）和 `horizontal_cover`（4:3 横封）在同一个对象里，一次翻页就能把横竖两张都拿齐，这是最省事的主来源。

### 匹配用作品 id，不要用标题

抖音清单必须**按 `aweme_id` 索引**，不能按标题。各平台标题是分别填的，同一个视频在抖音常被改短：

```
仓库主题：DeepSeek出了个新东西，这回是真能帮你干活|deepseek harness上手体验
抖音标题：DeepSeek 出了个新东西，这回是真能帮你干活
```

按规范化标题匹配时这两个不相等，整条就漏了。实测 129 期抖音作品里有 **36 期标题与仓库主题不一致**，那批的横竖封面全被漏掉（缺 3:4 的 22 期里 21 期都是这个原因）。`aweme_id` 与视频一一对应，标题怎么改都不影响——`data/videos.jsonl` 里抖音 url 全部带数字作品 id，取得到。

### 拿不到的情况

- **视频号的图只能当场在浏览器里看，命令行拉不到。** 图片地址里 `encfilekey` 要服务端结合登录态解密，`curl` 一律 `400`（`X-retmsg: decrypt encfilekey failed`）；刚生成的地址立刻下载、或在新标签直接打开，也是 `ERR_INVALID_RESPONSE`。别在这上面反复试 curl。
- **抖音的图有签名有效期**（`x-expires`），清单要现抓现用，过期就是 403。别把带签名的地址写进仓库或逐字稿。
- **B 站后台的 `cover43`**（2560×1920，比小红书那版更清楚）只在 `member.bilibili.com/x/vupre/web/archive/view?bvid=` 里，且必须登录、必须逐条请求；公开接口拿不到自己的这一张。只有确实需要高清素材时才值得跑一轮。
- **作品被平台下架或删除的，封面就真的没有了。** 比如 2026-09-10《WorkBuddy 接入 GPT、Gemini、Grok》，它的抖音作品 id 不在账号 131 条作品里，平台侧已不存在，只剩 B 站的 16:9。这是真实缺失，不要凑数。

### 分寸

- **别把不同期拼在一起**：三张必须来自同一期视频。曾经把 A 期的 4:3 和 B 期的 3:4 拼进一张对比图，看起来完全合理，结论却是错的。
- **抓完跑 `--verify`**：它逐张量真实宽高，核对索引与磁盘、尺寸记录、槽位方向。比肉眼看页面靠谱。
- **只缩不放**：原图小于 800 就保留原尺寸，从已经压小的图上放大，画质不会回来。
- **缺一张不算失败**：某一期只有一个平台发了，就只存那一张，不要拿相邻期或别的比例凑数。

## 模式判断

用户未输入编号、而是输入具体问题或场景时：

- 先判断场景诉求：
  - 做事（剪片、发布、装工具、搭工作台）→ 查编号目录（`catalog.json`），匹配编号方案，说明推荐理由，按该编号规范带用户执行，交付立即可用的结果；
  - 想事（困惑、纠结、寻求建议或观点）→ 进入上方「逐字稿模式」；
  - 看数据（询问视频表现、爆款复盘、平台对比、限流避坑）→ 进入上方「自媒体数据模式」；
  - 更新数据（「刷一下播放量」「同步各平台指标」「更新数据」）→ 进入上方「指标更新模式」；
- 多种诉求混合时，先用数据与逐字稿回应困惑与分析，再递上对应的编号工具。
